# Soundcheck: design

Soundcheck runs an app's regression suite on Android, iOS and web with AI agents as the testers, and reports results you can trust while the run is still going. It's one generic product: a project plugs in its test cases and a little config, and soundcheck does the rest.

This document is the design agreed on 2026-10-20. It's for whoever builds soundcheck, human or agent. Nothing is built yet. Its first user is Solo Scores, which will prove the concept; its migration notes live in that project, not here.

---

## 1. Principles

- **A run needs no babysitter.** The suite runs start to finish on its own: the server starts each spec, launches its tester and has every claim reviewed as it lands, verified where it needs to be (3.2, 3.3), so a run waits on neither a person nor the coordinator's next turn (SA-1049, Aled 2026-11-25). The coordinator starts the run, steps in when the server asks for it, and goes through the report with the person at the end, who decides what to do with the findings. The person can stop a run at any time by asking the coordinator; there's no special case for major bugs. See 3.10.
- **Every check is something a user does.** A spec is a user's goal in plain words. Nothing is checked twice, and a pass means what it says.
- **Android, iOS and web are equal from the first version.** The interface, element model, spec format and config are designed for all three at once.
- **Results and judgments show in real time,** presented exactly as the final report will show them. The person may look in at any moment to decide whether to stop, so every result and every review call reaches the page within seconds.
- **Machinery, not discipline.** Anything that went wrong because someone forgot a step becomes a state the server tracks and enforces.
- **The server never makes a judgment call** (SA-1049, Aled 2026-11-25). It orchestrates: what runs next, on which device, and when to wait are rules. Anything that needs a decision goes to a reviewer, or failing that to the coordinator.
- **Trust comes from:**
  - evidence filed against the exact build installed;
  - no unconfirmed result ever shown as a result;
  - parity tests for every reader against the platform's own tool;
  - verdict rules with no special exemptions.
- **Pieces, not the picture.** Driver tools are generic and parameterised, so they make sense unchanged in an unrelated app. No app's labels, flows or names enter soundcheck.
- **Emulators, simulators and local browsers only.** Physical devices are refused: they may run builds that point at production.

## 2. The pieces

| Piece             | What it is                                                                        | Knows about                                                                            | Lives in                             |
| ----------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------ |
| **Server**        | One long-running process per run: drivers, dispatch, journal, live page, report   | Suites, results, builds; the project via config                                        | `soundcheck` (Rust, `crates/server`) |
| **Drivers**       | One module per platform behind one interface                                      | Devices only; never tests, rows or the app                                             | `soundcheck` (`crates/driver`)       |
| **Plugin**        | The Claude Code plugin: binary, MCP config, skills, a SessionStart hook           | How to set up, run and author a suite                                                  | `soundcheck` (`plugin/`)             |
| **Project skill** | The project's own regression skill                                                | How to run its suite: accounts, device setup and quirks; takes a scope from its caller | The project                          |
| **Suite**         | Specs, `suite.yaml`, hook scripts                                                 | The app and its users                                                                  | Inside the project skill             |

The driver is a separate crate, so the compiler enforces that it never depends on the server.

### Who does what at run time

| Part            | Is                                                                                                     | Does                                                                                                                                                                                                                                          | Never does                                                           |
| --------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **Server**      | The `soundcheck` process                                                                               | Owns devices, device health, build identity, row states, the journal, evidence capture, the live page and report; readies each spec, starts it, and launches its tester and its reviewer                                                      | Makes a judgment call: judges a non-pass, or closes a run            |
| **Coordinator** | The Claude session the person talks to                                                                 | Starts the run, then waits to be asked for: a run that paused itself, a review no reviewer settled, an install or restart that failed. Pauses, queues and installs fix builds on request, finishes, triages the findings list with the person | Drives a device, starts a tester, or holds results in its own memory |
| **Testers**     | One headless Claude per attempt, launched by the server (`soundcheck-tester` or `-mechanics`)          | Drive the device through the server's tools, post the spec's result with evidence                                                                                                                                                             | Read app source, run shell, settle results, talk to the person       |
| **Reviewers**   | One headless Claude per row with a claim or side finds, launched by the server (`soundcheck-reviewer`) | Settle the row's claim and side finds from the evidence, reading the project's files where that settles a call                                                                                                                                | Drive a device, run shell, edit files, talk to the person            |

It's hub and spoke with the hub as code (SA-1049, Aled 2026-11-25): the server hands out the work and takes the results, which works because a run's subtasks are known up front. Until then the coordinator was the hub, and 3.2 says what that cost.

How they talk:

- **Server → tester:** it launches the tester with its brief as the prompt (3.2). After that, only in the reply to the tester's next call ("device degraded, stop"). MCP notifications don't wake a Claude agent, so nothing relies on them.
- **Tester → server:** MCP tool calls, over HTTP straight to the run's server.
- **Server ⇄ reviewer:** the same: launched with everything about its row as the prompt, and it answers with `review` and `review_find` (3.3).
- **Server → coordinator:** `soundcheck attention <run folder>` (SA-1051, Aled 2026-11-25). The coordinator runs it in the background; it waits, however long, until something needs the coordinator, prints it and exits, which wakes the session. It keeps its own cursor in the run folder (`attention.cursor`), so running it again misses nothing. It speaks for: a pause the server made (the coordinator's own is no news to it), a review left unsettled, an `install_build` ending (installed or failed), a device restart failing (the first failure, not each minute's retry), every row filed, and the server stopping. Before it waits it checks that the server at the run's address is this run's: `server.json` outlives its server, and another run may hold the port. The coordinator says nothing to the person between wake-ups; the live page shows progress. It replaced a Monitor on `soundcheck events`: that expired every 30 minutes and needed a hand-written filter and a cursor kept by the coordinator, and every line it let through cost a turn that re-read the whole context. `soundcheck events` stays, for looking into a run.
- **Coordinator → server:** MCP tools or the CLI (start, queue, review, pause, resume, install a build, finish, triage). It reaches testers only through the server, so every instruction is in the journal.
- **Server → live page:** a Server-Sent Events feed on the same port (`/{run}/updates`, 2026-11-04, SA-864): `view`, the run as one JSON view (built in Rust, so the page only lays it out), on every connect, then `patch`, RFC 7386 merge patches against what that page last got, sent only when the view changes, and a `ping` every 15 s so a dead link shows as "Not connected" within 35 s. The page follows it with `EventSource`, which resyncs from a whole view on each reconnect, and replaces it after a backoff when it gives up (a non-200 such as an expired ngrok sign-in). The page is a small Preact app (`crates/server/report-app`, bundled and checked in), so an update touches only what changed and scroll, open rows and selection survive it; the old page re-rendered whole on every journal event.

## 3. Server

### 3.1 Transport

- One process listens on localhost over HTTP: MCP (streamable HTTP, `rmcp`), the live page, its feed and the event stream share one port. The plugin's MCP config runs `soundcheck mcp`, a stdio bridge that forwards the coordinator session's tool calls to that URL; the testers and reviewers the server launches are given the URL itself (3.2).
- **Remote viewing** (`--remote` on `run` or `serve`, 2026-10-28): the person watches from a phone or tablet on another network. Soundcheck starts `ngrok` for its port with a traffic policy it writes: Google sign-in, only the suite's `remote.allow` emails, GET and HEAD only, and only the page's own paths (never `/mcp`). The policy rewrites `Host` to `127.0.0.1:<port>` and drops `Origin`, so the local-only check below still holds for everything else. A tunnel that fails to start is a warning, never a failed run. The run's server holds the tunnel, so `soundcheck remote <run folder> on|off` opens or closes it on a run already going (or still starting: `server.json` is written as soon as the server listens), with the same sign-in and allow list, and prints the address; it closes with the run (SA-928, 2026-11-06: run 8eb61013 had to be restarted as 9decb1a9 only to get the link). The page is installable (a web manifest and icons, no service worker), so it opens full screen from a home screen. Tried and dropped: embedding the page in Claude (nothing rendered on the iPad), and Tailscale (an app on every device).
- **Why not stdio:** Claude Code starts a stdio MCP server once per agent, which would mean several processes fighting over the devices and the journal.
- **Local callers only, with no secret.** It binds to 127.0.0.1, requires a `Host` of `127.0.0.1:<port>` or `localhost:<port>` (which stops a page whose domain was rebound to 127.0.0.1), and refuses any `Origin` but its own (agents and the CLI send none; the live page sends the server's). A token or fixed secret was dropped: any local process could read it and drive the emulator over adb anyway, and it would stop the plugin's MCP config being a plain fixed URL.

### 3.2 A run

1. **`soundcheck run <suite>`** (the coordinator starts it) runs a **preflight**: a fixed checklist, printed as each step passes, journalled for the timeline, and refusing to start at the first failure with what to fix. Deterministic on purpose: preparation is never an agent's judgement call.
   - lint the suite and check its pinned version;
   - take the port (SA-697);
   - check that `claude --version` runs, the first check on the page: the server launches every tester and reviewer with Claude Code (below), so a missing one is said before anything is built;
   - with stack hooks, remove any stack a stopped server left and start a blank one per platform (3.11);
   - run the project's `guard` hook (the project decides what "safe and up" means, e.g. local only, backend answering);
   - connect every device before anything is built: one emulator on API 34 or newer, one booted simulator, Chrome (SA-705), so a device problem shows in seconds rather than after a build;
   - wait for a settled Mac (SA-699);
   - read each platform's build identity; build and install with the `install` hook where it's unknown (every platform with `--install`), and refuse if it's still unknown. Web is built the same way (SA-840, Aled 2026-11-03): the `install` hook builds the app and records it, the start hook only serves the last build, and the server starts the web app again after every web install, at run start or through `install_build`. Before this the start hook built and served in one step, so `--install` failed on any run with web and a mid-run web fix needed a new run;
   - then open the live page.

   The project supplies every specific (hooks, each spec's `prepare` steps); soundcheck supplies the sequence and the generic checks, so it stays project-agnostic.

   **A start that fails keeps its run** (SA-1054, Aled 2026-11-25): the run's id is printed before the checks, with the page's address, and once what stopped the start is fixed, `--open <id>` starts it again as the same run. Before, a failed start deleted its folder, so the id and a remote link already given out died with it.

2. **Dispatch, one spec at a time per platform, by the server** (SA-1049, Aled 2026-11-25). Once preflight passes, the server runs dispatch lanes: one shared lane when platforms take turns, which keeps the run's order, and one per platform with `parallel: true`, so one platform's reset never holds up another's. A lane asks for the next row whenever something changes (a journal entry, a nudge) and every 15 s while a platform is held, so a hold (a busy Mac, a restart, an install, the health sample after a result) is waited out by the server and nobody has to watch for its end. The pick is the one the coordinator's `next` used: queued rows (send-backs, verifications, stalls) first, then rows never run, each in the run's spec order with a spec's platforms in turn, on the first platform that isn't held. A pick claims its platform as it goes, so two lanes never start on the same one (SA-927). Taking a spec's platforms in turn means a platform held late doesn't leave all its rows to the end. To run a particular spec now, the coordinator queues it (3.4): queued rows go first.
   - **Why the server, not the coordinator.** Until this, the coordinator dispatched: it started a background tester agent per spec, and the plugin's `PreToolUse` hook turned that call into a dispatch (2026-10-27), so that no value passed through the coordinator's hands. Each spec still cost it a turn. In Solo Scores' run 2d469187 (0.3.5, 93 rows on iOS and Android: 99 attempts, 3.3M tester tokens, 79 minutes of tester time) each clean pass cost one coordinator turn that re-read its whole context (453k by the end), which came to roughly as many tokens as all the testers read; a median 15 s sat idle between a result and the next dispatch, about 6.3 minutes in every 30; a pass woke the coordinator up to three times (the tester's hand-back, the task notification, the Stop hook); and a busy-Mac hold cost three coordinator turns. The person uses the coordinator to start the run, keep it on track, answer questions and triage at the end, and reads progress on the live page, so none of those turns were for them.
   - **What went with it:** the `dispatch` tool; the plugin's `PreToolUse`, `Stop` and `PostToolUse` hooks and their `/dispatch` and `/next` endpoints (the `Stop` hook blocked a coordinator from ending its turn while a row could start, and `PostToolUse` told it of a row freed mid-turn: both existed only because a coordinator that stopped listening stopped the run); attempts "handed out" between a `dispatch` call and its Agent call (SA-926); coordinator sessions registered with the server; and the tester's one-line hand-back, which was what woke the coordinator.
   - The server runs the platform's `guard`, relaunches the app (on `chrome`, at the spec's `viewport` or else the platform's), then runs the spec's `prepare` steps in order (5.6). A failure there (a step exiting non-zero or passing `--prepare-timeout`) is a **reset error**: retried automatically (twice), never counted as an attempt and never blamed on the tester or the app. If it persists, the server restarts the device (relaunches Chrome, or restarts the simulator or emulator) on a task of its own, as for a degraded device (3.7), and the platform is `held: restarting …` with the row still queued. Only when the next reset on the restarted device fails too is the spec filed BLOCKED "reset failed" with the server's capture, a harness block that isn't counted as tested. A restart that fails keeps the platform held, is journalled as `restart-failed`, and is tried again a minute later (SA-925, 2026-11-06: in run 9decb1a9 a wedged Chrome filed help/004, playlists/001 and playlists/002 BLOCKED without ever being relaunched). Chrome restarts as a fresh launch: the old browser is asked to close, killed if it's still there, and reaped, so one that crashed or was killed leaves no zombie (verifying SA-925 in run c0192647 found Chrome had no restart at all). A dead browser costs each reset its 30 s request timeout first, so the restart comes about 90 s after the crash.
   - It renders the tester's brief (the spec, its `_feature.md`, the suite's `_suite.md` (5.1), the platform hints and a spec token) and records it in the journal.
   - **The tester is a headless Claude process the server launches** (SA-1049, Aled 2026-11-25): `claude --print --agents <run>/agents/agents.json --agent soundcheck-tester --mcp-config <this server's /mcp URL, over HTTP> --strict-mcp-config --setting-sources "" --allowedTools <the agent's tools> --disable-slash-commands --no-session-persistence --output-format stream-json --verbose --model <the spec's model>` (the suite's `models.default` when the spec names none), with the brief on stdin and the run folder as its working directory. It runs on the person's Claude subscription. Such a tester sees only the tools it's given (named `mcp__soundcheck__<tool>`, plus Read for its own screenshots) and nothing of the project's CLAUDE.md, settings, hooks or plugins, and it starts at about 15k tokens of context with its instructions, its tools' schemas and its brief all in (measured on Solo Scores, 2026-11-25), where a subagent tester started at about 13k and then fetched a brief of 3k to 8k. The launch sets `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` (0.4.1): `--setting-sources ""` leaves Claude's auto-memory on, and a tester started inside the project's repository was given the person's memory of that project, about 11k tokens on every turn of the first 0.4.0 run. The server's own tester tools (`judge`, `post_result`, `check_data`, `act`) are listed beside the driver's, and a test keeps that list in step with the tools the server marks for testers: 0.4.0 left out `check_data` and `act`, and a spec that needed one was filed BLOCKED. The agent types' definitions live in the server and are written to the run folder at each launch, so the plugin ships no agents and a tester always matches its server. `SOUNDCHECK_CLAUDE` names another program to launch, for the server's own tests.
   - **The brief is the tester's prompt,** so it has no `brief` tool to call first. The brief had been kept out of the coordinator's context since 2026-10-23 (3–8k tokens each, twice over, ran a long run's coordinator out of context), which took a `brief` tool and a call; with no coordinator in between, neither is needed. The fixed contract (how to post, a person's pace, fewer calls) moved from every brief into the tester's own instructions, the same for every spec, so all testers share it as one cached prefix.
   - **Two tester types, so most testers don't carry the mechanics** (2026-10-26). `soundcheck-tester` has the basic tools; `soundcheck-tester-mechanics` adds the mechanic tools (4.1), and the server launches it only for a spec that lists `tools`. Every tool's schema is sent on every turn of a tester's: the five mechanics are about 4 KB (about 1k tokens) of the testers' roughly 23 KB of tool schemas, and only about one spec in nine lists one. Lint already refuses a mechanic a spec doesn't declare, so nothing a tester needs goes. The two agents' instructions are one text.
   - **Each agent's whole output stream is kept** in the run folder (`agents/<token>.jsonl`; a reviewer's is named for its row), for when someone asks why one did what it did, and its tokens are read from it (3.4).
3. **The tester works** through the driver tools and posts the spec's result once, with evidence. Nobody reads its final reply: everything is on the server. A tester whose attempt is settled (posted, stalled or abandoned) gets 60 s to end by itself, then is stopped.
   - **A tester that can't run pauses the run.** One that ends in error without posting (Claude not found, a usage limit, a model it doesn't have) pauses the run with the reason, so the remaining rows aren't thrown at the same wall, and the coordinator is told (below). If it ended before making any tool call, its row goes back to the queue without using an attempt (`interrupted`), since the harness failed it; otherwise it counts as a stall (3.3). A tester that ends cleanly without a single call pauses the run the same way: a Claude that couldn't reach this server exits without error, and nobody would otherwise hear until every row had used its three attempts. So does a build the `build-identity` hook can't identify (3.8): it refuses every dispatch until a person acts, and a coordinator used to read that refusal. A tester or reviewer the server stops as it shuts down is neither a stall nor a failure: the spec goes back first when the run is opened again (3.4), and each agent runs in a process group of its own, so a Ctrl-C at the server's terminal reaches only the server.
4. **When a spec finishes,** the server files a clean pass, and a claim or side finds get a reviewer (3.3). Nobody is woken. The platform is then held while its health is sampled (`held: sampling the device's health after the last spec`, 3.7), and its lane starts the next row once that's done.
   - **A new session hears about the run** (2026-10-27). The plugin's `SessionStart` hook, the only hook left, adds a short context line when a run's server is up: the run folder, label, verdict, rows left, anything running or waiting for review, that the server dispatches and reviews by itself, and a pointer to the run skill, so a coordinator after `/clear` knows where it stands. With no run up it adds nothing.
5. **Close:** the run stays open until the person says it's done: filing the last row doesn't close it (SA-784, 2026-10-28). The coordinator calls `finish` then, which stamps the verdict and writes the final report. The server refuses while any result is unreviewed or any spec is still running, and names what blocks it. Queueing a spec or adding a platform afterwards opens the run again. Sections have no closing step: each grid tile always shows its live state.

Platforms run serially by default (`parallel: false`). All state is kept per platform (a dispatch lane, a device, an account, a reset), so `parallel: true` runs one spec at a time on each platform, side by side (SA-779, 2026-10-28). It needs each platform on its own backend and proxy (3.11, 5.2), or one platform's seeds, revokes and faults reach the other: lint refuses it with a shared proxy. Each platform's driver has its own lock, so one platform's long call (a `wait`, a restart) never holds up the other's, and each platform has its own dispatch lane in the server (above), so none sits idle waiting for another. Host holds still apply to each dispatch: a Mac under critical memory pressure or a pegged CPU waits before the next spec on either platform.

### 3.3 Row states

Each spec on each platform moves through `not run → running → needs review → filed`, and the server owns every transition. A non-pass then goes through two separate decisions: **review** (is the claim real?) during the run, and **triage** (what do we do about it?) with the person.

- **A PASS** files at once, provided it has evidence for every outcome.
- **The tester judges each outcome,** not the spec: **held**, **failed**, **unsure** (observed, but it can't tell whether it's right) or **couldn't check** (never got to observe it). The server derives the spec's claim: any failed is FAIL, else any couldn't check is BLOCKED, else any unsure is **Unsure**, else PASS.
- **Final results are only PASS, FAIL or BLOCKED**, each resting on specific outcome lines. Unsure is never final.
- **A FAIL, BLOCKED or Unsure** becomes `needs review`. On the page the row reads **"Checking"** (the tester reported a problem and a reviewer is checking it; it's the harness's job, not the person's), with no age on the row. A check that stalls shows in the sticky bar instead ("checking annotations/003 for 6 min", in amber). It should last only minutes.
- **Review** is a reviewer's (SA-1050, Aled 2026-11-25): a short-lived headless Claude the server launches for each row with a claim (FAIL, BLOCKED, Unsure, a pass with untried probes), side finds waiting, or both, judging the tester's evidence and the server's capture.
  - **How it's launched:** like a tester (3.2), but in the suite's git repository, with Read, Grep and Glob plus `status`, `review` and `review_find`, so it can read the project's files when knowing how the app is meant to behave settles a call. Its model is the suite's `models.reviewer` (default `opus`). At most 2 run at once: each is a Claude process beside the devices on the same Mac.
  - **Its prompt carries everything about its row:** what the run is testing (`soundcheck run --about "<text>"`, kept as `about.md` in the run folder, so a run opened again tells its reviewers the same), the spec, the claim, each judgment with its observed text and the paths of its evidence, the server's capture, and the row's side finds. It needs no `status` call; when one is made for a row, `status` with a `spec` returns only that spec's rows, problems, waiting side finds and the evidence folder (SA-1052), not the run-wide notes and counts, which grow all run and were re-read at every review. Its rules are its own instructions (`serve/reviewer.md`), which were the run skill's review section.
  - **One row, one fresh context.** Before this the coordinator reviewed every claim itself, in the one context that also dispatched and grew all run (3.2).
  - **A reviewer that ends without settling its row is tried once more;** each gets 10 minutes. After two, a `reviewer` journal entry with `unsettled` leaves the row for the coordinator, which `soundcheck attention` tells it (section 2), and it reviews with the same tools. The coordinator also reviews when the person disputes a reviewer's call.
  - **It never asks for a harness rerun:** only a person who has fixed the gap does, through the coordinator.

  A review does one of these:
  - **uphold:** the evidence is conclusive. A FAIL is filed, and goes into Problems as a **failure**. For a BLOCKED claim (the tester couldn't check), the review says what stopped it: the **app** (it crashed, a screen wouldn't load), so the row is filed **FAIL** with a failure; or the **environment or harness** (a missing label, a tool that can't reach a control), so it's filed **BLOCKED** with a note.
  - **verify:** the evidence isn't conclusive. A verification attempt is queued: a new agent on a fresh reset, **told the claim** ("the first attempt saw the stroke survive undo; reproduce it"). Reproduced: upheld. Not reproduced: filed as a finding marked "not reproduced (1 of 2)", never silently dropped, since flaky problems matter at triage.
  - **resolve an Unsure:** judge it from the evidence (PASS or FAIL, with a reason) or verify it, telling the new agent exactly what was unclear. A verified Unsure that passes files PASS and nothing else: only a FAIL that doesn't reproduce becomes a "not reproduced" finding. Still unclear after verifying: filed BLOCKED with "spec unclear", and the spec is flagged for rewording with `create-test`, since ambiguity almost always means an outcome is worded too vaguely.
  - **send back:** the tester erred (a misread screen, a wrong tap, a device glitch), so a fresh attempt is queued without the claim.
  - Every call carries one line of reasoning ("upheld: the screenshot shows the stroke after undo"), shown on the row with whether it was verified or a single attempt, so the person's review at the end is an audit of the reviewers' calls.
  - All attempts stay in the journal.
- **Triage** happens in chat: the person with the coordinator, who records each decision through the server and creates the tickets, so the page (read-only) updates live. Matching a problem to an existing ticket is collaborative, never automatic (Aled, 2026-10-21): the coordinator searches the tracker and suggests a ticket; the person says whether it's the same bug (recorded under that ticket) or similar but its own (a new ticket, linked to the existing one). It's usually at the end of the run but possible at any time (a serious problem mid-run may need a fix decision straight away). Each open problem is:
  - **dismissed**: not a bug, or not reproduced;
  - **fixed**: the fix lands;
  - **deferred**: it's accepted for this release.
  - Tickets are optional (SA-703, 2026-10-25): a suite that names a tracker (`tickets`) needs one for fixed and deferred, and one without keeps findings in the report only, where each decision's reason is the record. One rule, no mode switch, so a project without a tracker can still triage. A trial on uncommitted code (3.12) files no tickets, tracker or not.
- **Side finds:** a tester that finds a problem outside the spec's outcomes while probing posts it as its own finding, linked to the row. The row keeps its own result, and the finding is reviewed like any non-pass. Its id (for `review_find`) is on the posted event's line and in `status`, beside its summary. Probing near old bugs is where new ones turn up.
  - **A finding's screenshots are on its topic** (Aled, 2026-10-21). They're there to help the person understand the problem, not to prove it: a finding about the eraser slider showed pen marks, which told him nothing. A side find never inherits the server's end-of-spec capture; that stays with failed rows. The tester attaches only shots of the control or screen the problem is about, including when the problem itself isn't visible (a spoken value): the screen may contradict the claim, and that's worth seeing. `review_find` keeps only the on-topic shots, whether they confirm the claim or not, and a finding with none says so on the page.
  - **Evidence on request** (Aled, 2026-10-21). When the person asks in triage for a screenshot of a problem, the coordinator reproduces it on the fly (the spec's `prepare` steps, then `soundcheck drive`) and `add_evidence` puts the shot on the problem, filed under its original attempt. It goes on whether it confirms the claim or contradicts it: a finding said the eraser slider read 102%, and a shot reading 100% is what starts the conversation that the text alone couldn't. No targeted-rerun command: the evidence is what matters, not a new result.
- **A spec whose tester stops** without posting goes back to `not run` with the reason, counted as an attempt, and is never left spinning. Stalled means no tool call for 2 minutes (configurable), counting only the time between calls: time inside a server call (a reset, a `wait`, a `sleep`, a `network-drop`) doesn't count. The clock starts at the tester's first tool call: before it, the limit is 10 minutes from dispatch (also configurable), since a slow network once delayed first calls past 2 minutes and every later call was refused. A tester that ends without posting stalls at once (2026-10-27): the server launched its process (3.2), so it sees it end, and an attempt still running then never posted, so it's journalled as stalled with "the tester ended without posting". (Until SA-1049 the plugin's `SubagentStop` hook told the run's `/ended`.) As a stall it counts as an attempt, so a tester that keeps quitting files BLOCKED on its third rather than looping, which a `queue` with a fresh budget would. The one exception is a tester that ended in error before its first tool call, which never got to test anything: its row goes back without using an attempt, and the run pauses (3.2).
- **At most 3 attempts per spec** (the original plus send-backs and verifications). After the third, the reviewer files what's known: BLOCKED with the reason, or the finding marked "not reproduced (1 of 3)". A flaky spec can't loop all night.
- **Not blocking:** a review never holds up the next dispatch. Unreviewed results block finishing the run; open problems block a Ready verdict, not finishing.

### 3.4 Journal

- Every event is appended to `journal.jsonl` before it's acknowledged: run start, dispatch with its prompt, result, review, device health, build installs and the reruns they triggered. A crash loses nothing.
- **A run folder is self-contained:** the journal, `run.json` (the suite, label, platforms and scope it started with), a snapshot of the suite's config, `_suite.md` and specs as they were, `summary.json`, the evidence, `about.md` (what the run is testing, 3.3) and `agents/` (the launched agents' definitions and each one's output stream, 3.2). Any run can be shown again from its folder alone, faithful to what it tested.
- **Opening a run again** (`soundcheck run <suite> --open <id>`, 3.8; `--resume <run folder>` still works) replays the journal with the saved platforms, scope and label. A spec that was running when the server stopped goes back to the front of the queue without using an attempt: the harness stopped it, not the app. `--platforms` on resume only adds: a platform the run lacks gets rows for its saved scope after its own preflight, `run.json` lists it and the journal records the addition, so one report covers both platforms. `--scope` on resume only adds too: specs new to the run get their rows, `run.json`'s scope and the snapshot gain them, and the journal records a `specs-added` event. The coordinator's `queue` does the same live, without a restart, reading new specs from the suite as it is now (they must lint clean). A closed run that gains rows opens again. A build that changed since the run last saw it is logged, never rerun by itself (3.8).
- **A run's label can change mid-run** (SA-764, Aled 2026-10-26): a run started as a fix check (sync and scores) was extended into the release regression, and still carried the narrow label. The coordinator's `relabel`, or `--label` on `--resume`, journals a `relabelled` event with the new label and why; the page, `/runs` and the export show the latest, and the journal keeps the history. `run.json` keeps the label the run started with.
- **Any spec can run again, whatever state its rows are in** (Aled, 2026-10-23, SA-716). After a harness fix, playlists/015's BLOCKED rows had no way back in once the run had finished. `queue` takes spec IDs or features: one not in the run joins it, one in it runs again with a reason the report shows. A filed result or a claim waiting for review is set aside, a running attempt is abandoned (its token stops working), and each row gets a fresh attempt budget; a finished run opens again. Adding and rerunning are one tool because they're one intent: run these. A `note` on `queue` is also how the coordinator tells one spec's tester something for this run only (a control that moved, an account to use): it's stored on the row, copied into that spec's next brief and then cleared. A note left by an attempt that a later one replaced says so in the report.
- **Where the time between specs goes** (2026-10-26): a `dispatched` entry is written the moment its reset (guard, relaunch, prepare steps, retries included) finishes, and carries `reset_ms`, how long that took, with each prepare step's command (as written, so no value it was given is recorded) and time; a failing step's command and reason are in the reset failure. So the gap after the previous `posted` splits into what came before the reset's start and the reset itself. Before the reset there's now only the health sample and any hold (SA-1049): the lane dispatches within milliseconds of the platform coming free, where the coordinator's lag was a median 15 s in run 2d469187 (3.2). `reset_ms` is a field on the entry rather than an event of its own, since every journal line woke the coordinator then.
- **What each attempt cost** (Aled, 2026-10-27): concrete numbers for cutting token cost, rather than notes kept by hand. The server counts a tester's token-carrying calls by tool and journals them with its working time (first call to last) as a `usage` entry when the attempt posts, stalls or is abandoned; a stall's silence isn't counted, and an attempt interrupted by a restart has none, since it doesn't count anyway. Tokens are read from the tester's own output stream when its process ends (SA-1049, 3.2), and journalled as `tokens` with the last turn's context and the input, cache writes, cache reads and output over all its turns (its closing `result` line's total, or the turns summed when it was stopped before one), which is what the tester cost. Until then the plugin's `SubagentStop` hook read the tester's transcript and posted to the run's `/tokens` (2026-10-27), and before that the coordinator relayed the completion notice's figure, which ran one tester behind; both went with the subagent testers. `soundcheck usage <run>` lists attempts with totals; `--compare <run>` pairs each spec on each platform with its last attempt in both runs; `--import <tsv>` backfills a run recorded before this (calls as a total, under `?`). The report header shows Active (the attempts' working time added up) and Tokens, and nothing per row.
- **What each reviewer cost** (SA-1059, Aled 2026-11-25): reviews are part of what a run costs, and since SA-1050 the server launches them, so it can count them. Each `reviewer` entry (3.3) carries the reviewer's tokens, read from its output stream as a tester's are (the last turn's context, and what its turns added up to), and its time from launch to end. `soundcheck usage <run>` lists the reviewers after the attempts and prints the whole run's total: every token testers and reviewers read or wrote, cache included, and their time. `--compare <run>` puts the two runs' totals side by side under the paired attempts. The page's Tokens figure adds reviewers' to testers'. The coordinator's own tokens are in no journal, since it is the person's own session and the server never sees its stream. That is why a run from before 0.4, whose reviews the coordinator did, reads as 0 reviews in a comparison: the comparison flatters the older run by whatever its coordinator spent reviewing.
- **The server is the only writer of results.** The report and live page render from the journal.
- **Location:** configurable in `suite.yaml` (`reports: <dir>`), one folder per run holding the journal, evidence and exports.

### 3.5 Evidence

- A tester attaches what it observed per outcome: tool output, plus screenshots for visual checks only.
- **On every non-pass, the server captures its own bundle** before replying: a screenshot, the element tree and recent errors/logs. The next spec's reset replaces the device state, so review must never depend on it.
- The server refuses a result that lacks evidence for any of the spec's outcomes.
- One evidence folder serves the whole run, so a tester's screenshot is saved as `<spec>-<attempt>-<platform>-<name>.png`, the server's captures' prefix. `post_result` resolves each attached name (bare, `.png` or full) to its saved file and refuses names that were never saved; the report also tries a bare name with `.png`, for older journals.

### 3.6 Build identity

- Read at run start, after each install, and before each dispatch (3.8), never on every filing (a device under memory pressure made per-filing queries take 40 s).
- **The driver reads generic facts:** app installed, version, install time. The project's `build-identity` hook turns them into commit plus fingerprint (mobile) or commit plus bundle hash (web).
- A build from uncommitted changes has no commit to identify it, so the hook refuses it, except in a trial (`run --uncommitted`, 3.12), whose hooks are told so and whose results aren't a regression result.
- Results file against the installed build. The release name in the run's config is only a label, so a stale install can't pass as the version under test.

### 3.7 Device health

- **Sampled after every result,** and journalled with that attempt as evidence. The platform is held while it's sampled (`held: sampling the device's health after the last spec`, SA-1049): the server now dispatches within milliseconds of a result, and the reading may call for a restart before the next spec. It reads:
  - Android: free memory (degraded under 10%), busy CPU over two seconds while the app sits idle (over 80%; not the load average, which post-boot disk work keeps near 20 with the CPU idle), ANRs in other apps since launch, and the app's launch time (`am start -W`, over 15 s);
  - iOS: the app's launch time (over 20 s).
  - The Mac, for the simulator and an emulator, which share it (a phone has its own): free memory (under 10%), the kernel's memory pressure (critical; warning is the steady state with both devices and dev tools up) and busy CPU over two seconds (over 80%), as host signals. Not the load average (SA-748): macOS counts threads waiting on disk, so when the simulator's background apps made the Mac page (2026-10-24), load read 60 to 155 with the CPU 60 to 70% idle. Not swap or compressed memory either: both stay high long after the pressure has passed.
  - Lost `adb reverse` forwards are put back on the spot: a reboot drops them, and the app then silently shows stale data.
- **When the host is busy** (a host signal past its limit), and while a degraded device restarts: the platform is `held:` and nothing starts on it. The platform's dispatch lane asks again every 15 s and starts the next row once it's free (SA-1049, 3.2), so the server waits out its own holds. Before that the coordinator did the waiting, first on a `ready` event (which stalled a run for 29 minutes when its event watcher missed it), then by running `soundcheck ready <run> <platform> --wait` in the background and dispatching again when it exited (SA-748, Aled 2026-10-25); a busy-Mac hold cost it three turns. `soundcheck ready` stays, for asking why a platform is held. After 10 minutes of holding, the server lets specs go ahead, and a host that never settles isn't held for again for 15 minutes. The dispatch that ends a wait journals it, a note in the record. A restart never answers a busy host: a booting simulator adds load, and on the first run (2026-10-21) restarts for the Mac's five-minute load fed a boot storm (`amsengagementd` and News at 100% each, load 140) that marked the next spec degraded too.
- **The run starts on a settled Mac** (SA-699, Aled 2026-10-25): before any build-identity or install hook, `soundcheck run` waits for the host signals the same way (every 15 s, at most 10 minutes). A build-identity hook then gets 60 s, and running out of time stops the run with the reason instead of rebuilding: on a settled Mac it means the hook is stuck, and a needless 14-minute build was what a 30 s timeout on a busy Mac cost before. A device that has stopped answering looks the same, so when the hook times out soundcheck first asks the device something quick (its screen's size, within 15 s); one that doesn't answer is restarted and the hook tried once more, and only a second timeout stops the run, saying to check the device, then the hook (SA-1053, Aled 2026-11-25: a hung emulator whose adb took 54 s was reported as "fix the hook"). Any other hook failure still means "can't identify the build", so an install hook builds it.
- **When health is degraded:**
  - the attempt is marked, and a failure seen on it can't be upheld until it reproduces: the reviewer calls verify, and the rerun runs on the restarted device. A harness BLOCKED can still be upheld;
  - the server restarts the emulator or simulator before the next spec on it, waits for it to settle, restores its forwards and reconnects its reader. Both are notes in the record. At most one restart per platform in 15 minutes, so a device that stays degraded is noted rather than rebooted in a loop.
- Health is part of the evidence. A slowly degrading emulator produced one-off failures that looked like app bugs (2026-10-20: 0.4 of 4 GB free, the system busy while idle, ANRs in Google's own apps, a 59 s cold launch).

### 3.8 Release runs and builds (SA-784, 2026-10-28)

The aim (Aled, 2026-10-28): the person manages a report's life, for flexibility and room for judgement; the harness keeps the evidence, it doesn't impose the structure. A run is something the person opens and closes, not something builds decide. A regression finds a bug, the fix is a new commit, and only the specs it could affect need running again: "this touched sorting, rerun those; the rest is the same". That only works if the run outlives a build. On 2026-10-28 it didn't: resuming the finished regression only to record a triage decision saw a new build and queued all 183 rows to rerun, so the verdict read "183 not run" and the export overwrote the report.

- **A run is opened on purpose,** with a title (`--title "Release 2.17.1"`, the old `--label`), and gets a UUID in `run.json`, printed at start. It's reopened with `soundcheck run <suite> --open <id>` (a unique start of the id, or the folder, also works; `--resume` is the old name) and stays open until the person closes it with `finish`. Filing the last row doesn't close it: the verdict says where it stands, and closing writes the final report. A run from before ids gets one the next time it's opened. Opening runs preflight for the devices but never changes a row.
- **Builds are evidence in the log, not structure.** Before each dispatch the server asks the `build-identity` hook which build is installed and journals a `build-installed` line when it differs from the last one on that platform, whoever installed it. A build the hook can't identify refuses the dispatch, since its results would be evidence for nothing. The hook runs on every dispatch (Solo Scores' takes under a second); filings never call it, which is what once took 40 s on a device under memory pressure (3.6). Each platform runs one spec at a time, so every attempt belongs to the build last logged before it: the journal stores no build on the row, and replay assigns it from the log.
- **A build change reruns nothing by itself.** The coordinator reads the diff and proposes the rerun set in chat, each spec with a one-line reason, and the person approves or changes it before anything is queued. That holds for a native change too: the proposal says it's native and why (a `patches/` change counts as native to Expo's fingerprint even when the patch is JS), and the person decides whether that means everything. Rows with open problems are in the proposal by default, since Fixed needs a pass after the fix.
- **A result stays until its spec runs again.** The verdict is each row's latest result. Which build a kept result ran on is read from the log (Aled, 2026-10-28: nothing extra on the page). Carrying it is the person's decision, made when they approved the rerun set.
- **Triage goes through the run's server, as before.** Opening a run no longer changes its rows, so reopening one days later just to triage it is safe; a separate serverless triage command was considered and dropped (Aled, 2026-10-28) as a second writer for no gain. If preflight's cost for a triage-only visit ever matters, the fix is letting `--open` skip devices and stacks when nothing will be dispatched.
- **Installs still happen between specs,** so no attempt straddles two builds, and platforms stay independent.
- **The server runs an install itself** (SA-922, 2026-11-06): `install_build` checks it's between specs, journals `install-started`, runs the `install` hook on a task of the server's own and returns at once. Its end is an event, which `soundcheck attention` tells the coordinator (section 2): `build-installed` with the reruns, or `install-failed` with why. A native build takes minutes, and run 9decb1a9's hook ran inside the tool call: Claude Code's session dropped mid-install, the hook died with the call, and Android was left with no app. One install per platform at a time; a second is refused. From its start to its end the platform is `held: installing a build` (SA-923): nothing starts on it, and its dispatch lane waits it out (3.2). A dispatch claims its platform and an install starts under the same lock, so one that passed its hold just before an install began can't start on the half-replaced app; an install doesn't start on a platform a dispatch is resetting.
- **An install asked for on a busy platform is queued** (SA-1058, Aled 2026-11-25): while a spec there is running or waiting for review, `install_build` answers `queued` instead of refusing. The platform is `held: waiting to install a build once its spec is settled`, so nothing new starts on it while the other platforms carry on, and the server starts the install by itself (`install-started`, then `build-installed` or `install-failed` as above) once the running spec has posted and its claim is reviewed; it looks at every journal entry and every 2 s. A second `install_build` for a platform with one queued or installing is refused. Why: since SA-1049 the server starts the next spec the moment one is filed, so "between specs" was a moment the coordinator could no longer hit. The run skill first had it `pause`, then call `install_build` again until it was accepted, and `resume` (the same day); that was a polling loop in a prompt for something the server already knows, and it was replaced before release. Known limit: a queued install lives in the server's memory and in no journal entry. If the server stops before the install starts, it's forgotten, and the coordinator asks again after reopening the run.
- **A failed install keeps its platform held** (SA-924): `held: install failed — <why>` until a later install succeeds or the `build-identity` hook reads the build on it again, which is logged as its build. An install still unfinished in the journal when the server stopped holds it the same way (`its install was cut off`), since the app may be half replaced or gone. The page's notes name each held platform and why. In run 9decb1a9 the plugin's hook offered Android straight after its install failed, with no app on the device.
- **Every mid-run install goes through the server** (Aled, 2026-11-06): `install_build` always runs the hook. Its old form, which recorded an install made outside soundcheck (`install: false`, or a `build` the coordinator stated), is gone and refused by name: soundcheck is in charge of what's built and installed, so it has no code paths for builds made by hand.

**What this removed:** `install_build`'s automatic reruns (every row on a new fingerprint, open-problem rows always), so reopening a run on a different build no longer re-baselines it, and the server closing a run by itself once the last row filed. `install_build` now reruns only the rows the coordinator lists. The older cross-report result transfer (Solo Scores' `report.mjs` carry and `map.json`) was retired on 2026-10-21; nothing else moves results between runs.

### 3.9 Report, live page, export

- **One UI.** The live page, the final report and the export are the same pages rendered from the same journal, so what the person watches during a run is exactly what they review afterwards.
- **Keep today's look.** The layout and styles of Solo Scores' current report (overview grid, section bars, overall ring, row and problem styling) carry over, adapted to the new workflow and data. Any design change beyond that is discussed with the person before it's made. Agreed so far: "Needs attention" hides sections with nothing to show (Aled, 2026-10-26).
- **What needs attention must be obvious at a glance.** Today's rows can bury it in a wall of text. Every row's detail follows one order (Aled, 2026-10-21):
  1. **anything that needs attention, as one coloured block:** red for a failure (the outcome that didn't hold, expected versus observed, and the review's call with its reason and whether it was verified); amber for a finding (what it is in one line, that it's outside the check, and a link to it in Problems);
  2. **the outcomes,** each with what was seen. Where a review settled an outcome (an Unsure judged from a screenshot), its note sits under that outcome, never in a separate box;
  3. **the evidence and the tester's notes,** collapsed.

  The collapsed row hints at a finding ("Passed · 1 finding"). The server enforces the failure block's input: a non-pass must name the outcomes it failed, with observed text for each.

- **The page header says what's happening now:** how long the run has been going and the spec running on each platform, plus "idle 20 min: nothing has started" once it's true. That's the only alarm an unattended run needs. It shows only while the server has work it could be doing (rows not yet filed, side finds not yet reviewed) and the run isn't paused. Once every row is filed the bar reads "Every row filed · waiting for triage" with no alarm: the run is waiting for the person, not stuck (Aled, 2026-11-25). Before 0.4 it read "coordinator not responding" and fired on any quiet run, since a quiet run then meant a stalled coordinator.
- **Page decisions** (Aled, 2026-10-21):
  - **Header:** the release label, devices, run start and last update. Commits stay out: the notes say which build each row ran on.
  - **A slim sticky bar while the run is live** says what's happening now ("Run · 1 h 12 min · Android · annotations/003"), and goes once the run finishes. One timer, for the whole run: per-spec timers and "last event N ago" were noise (Aled, 2026-10-21). A check or an idle run shows its time only once it's overdue, in amber.
  - **Rows show the spec's number within its feature card** ("001"); the full path appears on hover and in exports.
  - **Every row expands,** passes too, closed by default: a pass shows each outcome with what was seen, so you can check what it rested on.
  - **Problem titles are written by the reviewer** in plain words when it upholds a claim or a side find; the outcome-versus-observed lines sit beneath as the detail.
  - **One badge per problem, on the left:** an open problem shows **Failure** (red) or **Finding** (amber); a fixed or deferred one shows its ticket, or nothing without a tracker; a dismissed one a muted "Dismissed". The right side says only where it happened. "Verified" and "side find" go in the detail. The approved mockup: `design/report-mockup.html` (published at https://claude.ai/artifact/2vwanZhfugrneZJQqJq49Q)
  - **A collapsed timeline** at the bottom tells the run's story from the journal, one readable line per event. It replaces today's run log.
  - **Every run can be looked at, finished or not, without exporting:** a server lists all runs at `/` and renders each from its folder at `/{run id}/` (SA-785; a run from before ids uses its folder's name, and old `/runs/<folder>/` links redirect), and `soundcheck serve <suite> [--open latest]` does the same with no run going ("show me the previous report"). Exports stay single files, for sharing.
- **The report sections:** verdict rules (section 7), open problems, then triaged ones grouped as Fixed, Deferred or Dismissed, duplicates folded into their original, and time per spec and per run (plus agent cost where the coordinator can report it) so expensive specs stand out; nothing stops on budget; the notes hold harness gaps, device health and which build each row ran on. Ported from Solo Scores' `report.mjs`.
- **Light enough to sit open for hours** beside an emulator: animate only opacity and transform, and leave no spinner on a row nobody is working on.
- **Export:** a self-contained HTML file with screenshots embedded, which opens offline indefinitely.
  - Available at any time, from the page's **Download report** button (live or past run) or the coordinator's `export`. A mid-run export is stamped "in progress" with the verdict so far.
  - The final export is stamped with the verdict and build identities and doesn't change.

### 3.10 Unattended runs

Nothing in a run may wait for a human:

- **Permissions:** a Claude Code permission prompt must never be what stops an overnight run. The testers and reviewers the server launches are given their tools on the command line (`--allowedTools`, 3.2) and read none of the project's settings, so they can't prompt and no allowlist is involved (SA-1049). That's safe because a tester's only tools are soundcheck's own and Read, and a reviewer's are Read, Grep, Glob and three of soundcheck's. The allowlist is for the coordinator: the `run` skill pre-allows its tools and commands (`allowed-tools`), and `setup` adds `mcp__plugin_soundcheck_soundcheck__*` and the `soundcheck` commands it runs (`soundcheck attention` among them) to the project's permission allowlist, so a coordinator outside the skill doesn't prompt either. Before, that allowlist rule was also what kept background testers from prompting. The plugin's MCP tools are named `mcp__plugin_soundcheck_soundcheck__<tool>`, with the registry's hyphens as underscores; tests keep the run skill's and `setup`'s rules in step with that name.
- **Claude Code on the server's machine:** the server launches its agents with `claude`, on the person's Claude subscription, so it must be on the PATH where the server runs; preflight checks it (3.2). A usage limit reached mid-run pauses the run with the reason rather than failing the rows after it, and `resume` carries on once it has reset.
- **Accounts:** each platform's account is set up so seeding and sign-in never need a person (no account pickers, no device-policy prompts). `setup` checks this.
- **Stuck devices:** the server restarts a degraded or wedged device (3.7). If a spec still can't run, it's filed BLOCKED with the reason and the run moves on.
- **Where the coordinator runs:** an ordinary Claude Code session on the test machine. The run no longer depends on it staying awake: dispatch and review are headless, in the server (SA-1049, SA-1050), and a coordinator that's closed mid-run costs only the answers to what `attention` would have told it, which wait in the journal.
- **A coordinator that lasts hours:** all state lives in the server, so a compacted or restarted coordinator reconnects and carries on from the journal, and `soundcheck attention` picks up from its own cursor. Its context stays small because it takes no turn for a spec that passes or a claim a reviewer settles: it wakes only for what `attention` prints (section 2). In run 2d469187 a turn per pass had taken it to 453k of context (3.2).
- **Stop is pause.** When the person asks the coordinator to stop, the run pauses with everything in the journal; `resume` continues from the next spec. That covers "big bug: fix it, then carry on" with no special case.

### 3.11 Scratch stacks

A suite with `stack-up` and `stack-down` hooks (5.3) gives each platform its own backend, started blank by the run and removed when its server stops (SA-779, Aled 2026-10-28). Platforms then share no account, data or network, which is what lets them run in parallel: in the v2.17.0 run, one refresh-token reuse on iOS revoked the shared account and stopped Android's sync too. Every run starts blank, a resume too, so every spec's `prepare` signs the app in itself (below). What a stack is (containers, ports) is the project's business; soundcheck owns when one starts and that it's always removed.

- **A record per stack** (`<reports>/.stacks/<platform>.json`) names the server that owns it (its pid and start time, read in a fixed locale and time zone, so a reused pid isn't taken for it) and the command that removes it. It's written before the stack starts, so a server killed mid-start still leaves it to be removed.
- **On the way out:** Ctrl-C, SIGTERM, SIGHUP (the terminal closed), a step-down for a new run, and a failed preflight all remove the stacks, after the server has stopped. Signals are caught from before the stacks start, so one during a long preflight (a build) removes them too. Removal gives up after 2 minutes (a hung Docker) and keeps the record for the next try. Not when the run finishes: triage reproduces problems on the stack.
- **After a server that couldn't** (SIGKILL, a crash, the Mac restarting): the next `run` or `serve` removes every stack whose server is gone before anything else, and `soundcheck stack down` does it by hand (it also runs `stack-down` for every platform without a record). `soundcheck stack status` lists the records. A new run waits up to 2 minutes for a server stepping down (only on the platforms it starts; another server's other platforms are left to it), which frees the port before it removes its stacks; `stack down` refuses while a server is running, rather than pull the backend from under a run.
- **The project's stack never restarts itself** (no restart policy, data in memory), so a Docker or Mac restart doesn't bring one back, and nothing outlives its removal.
- **Signed in at every reset** (SA-881, Aled 2026-11-05): a blank stack doesn't know the device's session, and an offline-first app keeps showing it as signed in, so each spec signs in through its own `prepare` (5.6), with a project script and `soundcheck drive` tools. soundcheck has no sign-in or session concept; signing in through the real provider is a spec of its own, like any other feature.
  - **It replaced the suite's `prepare` brief** (2026-10-28 to 2026-11-04): a brief a tester followed once per platform before its first spec, signing in through Google's real screens, with `done` labels soundcheck checked. Its sign-in was state shared across specs: a spec that signs out or switches accounts (Solo's `account/007`) left the specs after it signed in as someone else, or not at all, and a resume or a new server had to prepare again. A seed hook returning a session to apply was tried on paper next and dropped (Aled, 2026-11-05) as the wrong abstraction: it built one project's idea of sign-in into soundcheck.
- **Known limits:** a `stack-up` that times out may leave Docker still starting the stack after its record is gone; the next `up` or `stack down` removes it. A backend that reaches its own services through the platform's proxy (Solo Scores' API signs and calls the bucket at one address) loses them too while a spec has that platform `offline`.

### 3.12 Uncommitted trials

`soundcheck run <suite> --uncommitted` tries specs on code that isn't committed yet, before committing it (0.3.1, Aled 2026-11-05). A commit can't identify that build, so a project's `build-identity` hook refuses it in a normal run; a trial says it may accept it, and says plainly that its results aren't a regression result.

- **Every hook is told:** each project hook the run starts (guard, `build-identity`, `install`, `serve`, `check`, `act`, `stack-up` and `stack-down`, and each spec's `prepare` steps) gets `SOUNDCHECK_UNCOMMITTED=1`. soundcheck adds it in one place for every hook command, so none misses it. What it allows is the project's call: Solo Scores' `build-identity` hook accepts a dirty tree's build only then.
- **Kept in `run.json`** (`uncommitted`), so it holds whenever the run is opened again (3.8), with or without the flag. A run started on committed code can't be opened with `--uncommitted`: a committed build's results and an uncommitted one's never share a run.
- **No tickets:** a trial is evidence for no commit, so nothing goes to the tracker. `triage` refuses a ticket on it and doesn't ask for one with a tracker; the reason is the record. Where a fixed or deferred problem's ticket would be, the report says "No ticket: uncommitted". `status` and the SessionStart context say it's a trial, so the coordinator doesn't offer tickets.
- **The page says so:** the live page and the report carry a banner under the title saying it's a trial on uncommitted code, not a regression result, and the list of runs marks it "Uncommitted".

## 4. Drivers

### 4.1 Interface

- **One registry of every tool** (`soundcheck_driver::TOOLS`): each entry has its name, its kind (basic, or a mechanic) and the platforms it runs on, and later its parameters, which are also its MCP schema. The MCP tool list, lint and the tester's brief all read from it, so no tool is defined twice. Basic tools are open to every spec; a spec lists mechanics in `tools`, and lint refuses one on a platform it doesn't run on.
- **Reading:**
  - `see [filter]`: the element tree;
  - `expect` and `gone`;
  - `check "A" "B" "!C"`: several assertions on one read;
  - `wait`;
  - `expect`, `gone` and `check` take an optional `timeout_ms` (at most 120 s): they read again every 250 ms until they hold and return as soon as they do, like `wait`, so UI that comes or goes late needs no pause first. Without it they read once, as before;
  - `sleep <ms>`: a plain timed pause, at most 30 s (the coordinator's `pause` pauses the run, hence the name). Only for when elapsed time is what's under test (a network drop's length, a session expiring); everything else waits for a condition. It stays its own tool rather than an option of `wait` (Aled, 2026-10-26);
  - `shot`;
  - `errors`.
- **Input:** `tap`, `fill`, `type`, `clear`, `swipe`, `hold`, `touch`, `release`, `keyboard`, `relaunch`.
- **Scrolled out of view** (SA-690, 2026-10-25): a scroll view reports children it has scrolled out of view, a paging grid's second page among them, and a tap on one landed on whatever showed in its place. Reads now mark such an element `off view` when one swipe brings it in (further away is left out, so a long list's read stays short), and `tap` and `hold` swipe its scroll view toward it, wait until it holds still, then touch it, as VoiceOver and TalkBack scroll to what they focus. Android's reader skips children that aren't visible, so it emits these with the scroll view's area; their bounds come clamped to that area, which still says which way to scroll.
- **`touch`: one finger along a path** (SA-715). Each stop is an element or a point, with a rest there; the finger moves between stops at a fixed finger pace, settles and lifts at the last. It covers any gesture a finger makes without lifting: slide off a control and back, long-press then drag, stop a slider partway. Every element is found before the finger goes down, so nothing is read mid-gesture. With `keep` the touch stays down at the last stop, so a tester can `see` or `shot` mid-gesture, until `release` (where it is, or `back` to its start so nothing drops), the next input or 30 s, which both go back first. It's the one finger-path primitive: a drag is two stops (`drag` was retired for it, 2026-10-23), `hold` is the one-stop case kept by name since a long press is its own everyday intent, and `preview-compare` holds its placement with a kept `touch`. Only `swipe` stays apart, since it lifts while moving to fling. The pace can't be set, for the same reason as `double-tap`'s rhythm. On web a kept touch is the mouse button held, lifted only by `release` or the next `touch`. A web touch resting with the button down sends its point again every 50 ms, as a desktop's drag session updates a resting drag (SA-1009, 2026-11-13): Chrome asks the element under the pointer to take a drop (`dragover`) only on the update after the one that entered it, so a drag lifted right after crossing into a row's label used to drop as refused and snap back.
- **Web-only:** `hover`, `goto` (back, forward, or close a tab the app opened), `viewport`, key shortcuts. They're in the interface from day one, and a platform without one refuses it clearly, so a spec never silently skips a step.
- **`batch`:** a sequence of steps that stops at its first failure. The failure says which step of how many failed, what ran before it, and the screen as it is then (a `see`), so a batch is no more brittle than single taps and the tester needs no extra call to find its feet.
- **Fewer turns** (2026-10-26). A tester's cost and wall time are both roughly its turns times its context: the run of 2026-10-26 averaged about 49 turns a tester, 13k tokens of context at the start and 34k at the median turn, mostly `tap`, `see` and `sleep`, with `batch` used 4 times in 18 transcripts. So testers are told (in every brief then, in their own instructions since SA-1049, 3.2) to `batch` the steps whose course they already know (open a menu, choose, confirm), to keep the checks an outcome is judged on as their own calls, and to wait for a condition rather than `sleep`. `tap` and `see` stay separate tools (Aled).
- **`soundcheck drive <platform> <command>`** runs the same commands from a terminal outside a run (Android and iOS; web has no browser to keep between calls), for exploring, reproducing a bug or setting up screenshots. Two more are for the harness itself: `parity` (4.3) and `keyboard hardware|software` (iOS).
- **Tools for mechanics an agent can't do one call at a time:**
  - `double-tap <target>`, which one tap call at a time is too slow to make: two taps 150 ms apart, a person's double-tap. A quick gesture gets its own named tool like this one, never a burst with a count or an interval a spec could set faster than a finger;
  - `network-drop <seconds>`, with the app in the background: nothing passes and nothing closes, as when a phone loses the network in the background. Connections open during the drop stay frozen until it ends and then close, as a real network change closes them (2026-11-03: left frozen, a web page reloaded mid-drop, and any request with no deadline, hung long after the drop, since Chrome reused the frozen connections); new ones get through after it. It returns once the network is down; with `wait` it returns once it's back, so a sync spec needs no `sleep` to sit out the drop. `wait` covers drops of up to 30 s, the longest one call may last (SA-761);
  - `offline` on and off: connections are refused and open ones closed, as in airplane mode, until the tester brings the network back. The run brings it back before every spec and after every attempt;
  - `fault <path> <status>` and `fault clear`: the proxy answers HTTP requests to that path itself with the status (400–599) and closes the connection, so the service never sees them, as when it fails or refuses one kind of request while the rest works (Aled, 2026-10-25: the app's sync-problem and refused-PDF states had no natural way to happen on the local stack). `*` is any one path segment and the query string doesn't count. Every request on a kept-alive connection is checked, and a websocket passes untouched after its upgrade. Setting a fault also ends open connections whose request in flight it matches, as a failing service drops a long-lived stream (PowerSync's), which would otherwise never see it. Faults stay until cleared; the run clears them with the network before every spec and after every attempt. On web the proxy also allows the page's origin on its answer, as the service's own CORS headers would, and lets a browser's preflight through, or the page would see a network error rather than the status (SA-813);
  - `match <name> <target> [fit]`: does a render hold up, across platforms and from one build to the next (Aled, 2026-11-01: annotation rendering had no check that app and web draw alike, nor that a render library upgrade changes nothing). It screenshots once the screen holds still, crops to the target's frame (or a `fit` shape centred in it, for a page inside a viewer that only labels its whole area), scales to the suite's reference image `references/<name>.png` and scores the share of ink that differs, after a slight blur and the best of a few pixels' shift, so density and antialiasing don't count. The reference's `exclude` (in its yaml, as fractions of the compared area) leaves areas out of the score on every platform, for controls floating over it (Aled, 2026-11-01: iOS's back and annotate buttons sit over the page's top margin, where no other platform has them); they show grey in the diff. It lives with the reference, not the call, so no tester can leave it out. The reference is one platform's capture a person approved by eye; `references/<name>.yaml` holds each platform's bar, which `soundcheck reference` sets from a run's scores and only tightens. With no reference or no bar it keeps the capture and says so, which is how a person makes the first one. Every call keeps the capture losslessly in the run's `references/` and the capture, diff and reference as evidence;
  - all three go through the suite's network proxy (5.2 `network`). Web routes its page too, so an offline relaunch can't load it from the server (Aled, 2026-11-01, SA-813: Chrome's own offline switch left open websockets up and never reached the service worker's fetches); a web suite without routes falls back on that switch, which can't `fault`. A suite without a `network` section can't use them on a device, nor `fault` on web, and lint says so (Aled, 2026-10-22: iOS had no way offline, and Android's airplane mode never cut the local stack, since `adb reverse` goes around it);
  - timed `hold` and `swipe`, and `touch` with its rests.
- **`judge`: progress as it happens** (Aled, 2026-10-23). A tester records each outcome with `judge` as soon as it's settled, so a running row fills in one outcome at a time instead of all at once on the post. Judgments are provisional: judging the same outcome again replaces it, and `post_result` takes them all up and files the result, so review and every rule after it are unchanged. Folding `judge` into `post_result` to save calls was considered and dropped (Aled, 2026-11-25): a spec's outcomes would land on the page all at once again. Until the review's call, the page shows anything that didn't hold as an orange ?, the same as the Checking cell; red and purple appear only once a result is filed.
- **A person's pace between actions** (Aled, 2026-10-23). Every interaction is one a person could physically and realistically make: the screen responds before the next action. The 2026-10-22 run filed findings for taps a few milliseconds into a drawer's close and for a second row tapped while the list shifted; the app was right each time, and no user does that. So testers are told to act at a person's pace and that a tap lost mid-animation isn't a finding, `batch` starts each input at least 500 ms after the last one ended, and a spec's probes never ask for the impossible. Single gestures keep their own fixed rhythms (`tap`, `double-tap`, `touch`'s pace).
- **Units:** milliseconds everywhere, and absurd values are rejected (an agent once passed ms to a seconds argument and waited 16 hours).

### 4.2 Element model

- Each element has label, value, id, role, frame, tap point, enabled, and checked/selected/expanded/focused.
- **It matches what a screen reader gets.** On Android the reader asks for the tree a screen reader is given: without the flag that includes views marked not important, so Android itself decides importance, as `uiautomator dump --compressed` does. Labels that are only a resource or test id are left out too, since a screen reader never speaks them. `see --all` gives everything. A hidden duplicate label once took a tap meant for the real switch.
  - **A labelled control reads as its label alone** (SA-781, 2026-10-28). Inside a focusable node with a content description, the plain text under it isn't read, as TalkBack reads it, and as VoiceOver groups it on iOS: a score row reads `Select score <title>`, not its title, artist, " • " and duration as well. A focusable control inside it (a row's menu) still reads. On a long list this was four lines in five of every Android read (the v2.17.0 run's long-list specs cost Android up to 70% more tokens than iOS); with it, Android's reads of the long collection, the drawer and Account match iOS's apart from iOS's icon labels and scroll bars. `see --all` keeps the text.
  - Filtering on each node's own importance flag doesn't work: on React Native every node reports "not important" (2026-10-21, Solo Scores read empty). Android's own tree is the reliable source.
  - The Android reader also asks for interactive windows, as TalkBack does, so Android counts a node the on-screen keyboard covers as not visible: a tap on it would land on the keyboard. uiautomator doesn't ask, and lists those nodes.
  - Both trees, everything and the screen reader's, leave out nodes that aren't visible to the user, as uiautomator does. That includes a control drawn outside its parent's bounds, which Android reports invisible with an empty frame (Solo Scores' Android text box Done, 2026-10-21): an app bug, since TalkBack can't reach it either.
  - Proven on the parity screen set (2026-10-21), and the default.
  - Expect a few label fixes in the app.
- **Label matching is explicit:** exact by default, with prefix or regex only when asked. An implicit match let `gone "Shuffle Order"` pass while `Shuffle Order…` was on screen.

### 4.3 Platforms

- **Android:** a persistent reader, an instrumentation APK that holds one `UiAutomation` connection and serves the tree over `adb forward`, plus adb for input. `uiautomator dump` is the fallback. Reads take 10–140 ms against about 3.5 s for `uiautomator dump`. It needs Android 14 (API 34) or newer; an older device is refused by name when soundcheck connects, and a missing reader is installed then (SA-695).
- **iOS:** a persistent Swift reader built on AXe's code, which keeps one simulator accessibility session and one HID session open, for reads and for all input. The HID session is built directly on the DTU transport: `connectToHID()`'s goes dead without an error after any `xcodebuild` that loads a workspace, a build or even `-list`, so taps land nowhere while reads still work (Aled, 2026-10-22, SA-688). There's no fallback for reads either: a reader gap is a bug to fix. A sheet another process draws over the app (Google's sign-in in SafariViewService and WebKit, Safari's sheet) isn't in the frontmost tree, and the bridge reads only that tree or the element at one point; so a find for `tap`, `fill`, `expect` or `wait` whose label has been missing a second asks `/describe?lean&others`, which hit-tests an 80-point grid (about a second) and adds what the tree lacks, and asks again at most every 3 s. Plain reads, `see`, `gone` and `check` never scan: a check on every read cost 13–60 ms and misfired to 2.85 s with the keyboard up (SA-790, 2026-11-04). The reader links idb's FBControlCore and FBSimulatorControl, which `readers/ios/build.sh` builds from source at the idb fork AXe pins (XcodeGen, about a minute, once per pin), so neither AXe nor its Homebrew tap is needed (2026-10-22). About 0.25 s per read, which is the simulator's own floor, and 0.1 s per tap. It also connects and disconnects the simulator's hardware keyboard (CoreSimulator's `setHardwareKeyboardEnabled`): connected for every spec unless it says `keyboard: software`.
- **Web:** `chromiumoxide` over the Chrome DevTools protocol, with Chrome's accessibility tree as the element model. It's chosen to keep one binary; we write our own waiting and snapshot code. Chrome runs headless; `soundcheck run --headed` shows it in a window to watch (look only: a click or resize can steer a test). A window the page opens (Google's sign-in popup) takes reads and input while it's open, as a person would be looking at it. A browser dialog (alert, confirm, prompt) blocks the page, so `see` shows it alone, as its message and Chrome's `OK`/`Cancel`; tapping one (or Enter/Escape) answers it, typing fills a prompt, and anything else is refused until it's answered. A file picker the page opens is held the same way (2026-11-01): `see` shows it alone, as a row for each file `push` staged and `Cancel` (rows tick, then `Choose`, when it takes several), and tapping a row gives the page that file; `push` works on web so specs that pick a file read the same on every platform. A download is saved into the launch's profile and listed at the top of `see` as `Downloaded <name>`, with its kind from the file's own first bytes and its size (`PDF, 34 KB`), until the next launch; the phones show a share sheet there instead. Headless Chrome reads as ordinary Chrome: services treat "HeadlessChrome" as a bot (PostHog returns it no feature flags).
- **Date and time fields are typed, not set** (SA-897, 2026-11-05). Chrome draws `date`, `time`, `datetime-local`, `month` and `week` inputs as segments that ignore inserted text and take only real key presses, so typing into one sends key events. Text in the field's own value shape (`2026-12-25`, `14:30`, `2026-W05`) is typed as a person would: from the first segment, each segment's digits in the order the field shows them, and its value is what `fill` checks, since Chrome's tree reports it as ISO. The order comes from the parts of the field's shadow tree (`-webkit-datetime-edit-day-field`…), which keep their names in every language; only a segment picked by name (a `month` input's month, AM/PM) uses the field's language through `Intl`. `fill` taps such a field at its first segment, not its right end, where the picker button is. Setting the value with the native setter and firing `input`/`change` would be shorter, but no person can do it, and an app that listens for keys or blur would see something it never sees in use. Not yet tried on a 12-hour field: Chrome on macOS takes its locale from the system, so the tests only see a 24-hour, day-first one.
- **Headless devices** (SA-683): drawing device windows loads the Mac (WindowServer was its busiest process on 2026-10-21), so the emulator and simulator run without windows by default too. An emulator soundcheck restarts boots with `-no-window` (still the host GPU), and a simulator needs only `simctl boot`; `--headed` shows the emulator's window and opens Simulator.app on the device. A device already running when the run starts is used as it is. Reads, input, screenshots and the keyboard switch all work headless.
- **Readers** are built by the soundcheck build (their `build.sh` scripts) and embedded in the binary. The server installs, starts and supervises them:
  - a timeout on every call;
  - a wedged reader is restarted;
  - after a device reboot, the forwards are restored;
  - **the iOS reader says who it is:** `/ping` answers `ok <udid> <build id> <pid> <started, unix seconds>`. `build.sh` stamps the build id (a hash of `Reader.swift` and the idb pin) into the binary and writes it to `reader.build-id` beside it. The driver replaces a reader whose build id differs from the one on disk, or that started before the simulator's current boot (its input session answers but lands nowhere). It stops a reader by the pid it reports, or the one listening on its port, and only then by its path: on 2026-10-23 a reader a `cargo test` had started (`crates/driver/../../readers/…`) took the server's taps, which did nothing, because the server looked for its own spelling of the path (`crates/server/../../readers/…`);
  - **a lost channel restarts the simulator** (2026-10-23, five times in one iPad run): a read failing with `Channel disconnected`, or a fresh reader that can't read within a minute (just after a boot it can't for 10–20 s), is mended only by a reboot. The driver stops the reader, reboots the simulator, starts a fresh reader and waits for it to read, at most once in two minutes. The app's state goes with the reboot, so the call that hit it fails with a harness error saying the simulator was restarted and the spec needs a rerun; a spec's reset that hits it relaunches the app instead. The next spec starts on the working reader, and the device's health event says `restarted the simulator: the reader lost its channel (…)`, as it says `restarted the reader: …` for a stale reader.
- **Long-lived at both ends.** The readers keep one accessibility connection open on the device, and the server keeps one connection to each reader, so a step never starts a process. Today's speed-up came from exactly this for reads: each `ui.mjs` call still started Node, ran the guard and set up adb.
- **Input goes through the readers too.** Today every action starts a process: an Android tap is `adb shell input tap` (0.7–0.8 s, and `fill` 2.0 s, measured 2026-10-20), and each iOS touch is a new `axe` process. The readers take input over the same connection instead:
  - **Android (done 2026-10-21):** `UiAutomation.injectInputEvent` inside the reader (`/input` scripts in the iOS reader's step format, `/type` through the device's key map), so taps, drags and holds cost milliseconds, and a `double-tap`'s gap is timed on the device rather than across adb round trips. No `adb shell input` fallback; an older reader on the device is replaced;
  - **iOS (done 2026-10-21):** the reader keeps the HID connection open for touches and typing, as it does for reads: a tap fell from about 1.3 s through `axe` to 0.1 s, and a `fill` from 15–58 s to 3–5 s. There's no `axe` fallback for input: a gap is a bug to fix.
  - **Taps keep a person's timing, and sub-frame races are out of scope** (Aled, 2026-10-21, SA-673). On the SA-437 bug build (a back tap blanking the app when press-in and release land in one frame), raw `adb input tap`s and injected taps held 0 or 10 ms broke it within three rounds, while taps held 20 ms or more (the reader's `tap` holds 80) passed 100 rounds; on the fixed build, 0 ms taps passed 60. So injected input reproduces such a race only with an unnaturally short touch. A regression suite isn't expected to catch a bug that edge, so taps stay natural rather than chasing it, and `tap-burst` became `double-tap` with a fixed 150 ms rhythm, since an 80 ms double Undo once left a state no finger could reach.
- **Device tests run only when asked for** (2026-10-26): the driver's emulator and simulator tests drive whatever device is running, and a plain `cargo test` during a live run once launched Settings on its emulator mid-spec. They run only with `SOUNDCHECK_DEVICE_TESTS=1`, the reboot tests also only with `--ignored`.
- **Parity tests:** every reader against the platform's own tool (`uiautomator`, Chrome's snapshot; iOS has none since AXe went, and AXe read through the same idb code anyway), on a fixed screen set that includes overlays, sheets, dialogs, menus and screens with the keyboard up. A reader change ships only after it passes.
  - `soundcheck drive android parity` compares the current screen, both the full tree and the screen reader's (`uiautomator dump` and `--compressed`): elements pair by label and nearest frame, then frame (within 2 units), value and states must agree. On Android, what only uiautomator lists under the keyboard is set aside (above).
  - **The screen set** (Solo Scores, 2026-10-21): a collection's home, the app drawer, a header menu, a settings sheet, the same sheet with the keyboard up on a field, a destructive confirmation dialog, and markup mode with a text box open and the keyboard up. Both platforms had parity on every screen.
  - It found two bugs: Android's reader showed invisible nodes in its full tree (a closed drawer's full-screen "Close drawer"), and the Android parser lost every value uiautomator single-quotes (any text holding a `"`).
  - **A reader on the device is always this build's:** connecting compares the installed APK's hash with the built one and reinstalls on a difference, so a reader change can't be shadowed by an older one still installed.

### 4.4 Ruled out

- **Appium:** temperamental, and it would replace the evidence layer for little gain. Our Android reader is the same idea Appium uses underneath, without WebDriver.
- **Maestro:** it waits for the UI to settle, which hid a real race (SA-437 passed 20 of 20 under Maestro on the bug build, while raw taps broke it). That race turned out to need a near-instant touch, which soundcheck doesn't chase either (4.3), but settling still hides ordinary timing a person produces.
- **Detox:** it needs test hooks compiled into the app, so it can't test the shipped build.
- **`idb_companion`:** breaks with new Xcode releases; AXe already worked.
- **Playwright for web:** mature, but a Node sidecar, and its auto-waiting is the settling behaviour that hid the race above.
- **A `stress` tool for device load** (removed 2026-10-21): a hammered device makes any app sluggish, and a test can only confirm that, with no bug behind it to guard. Busy loops on an emulator aren't a slow phone either (memory, GPU, storage, heat). If a load-dependent bug ever turns up: start the loops with `setsid nohup timeout <s> sh -c 'while :; do :; done' &` (plain `&` dies with the adb shell, which is why the first version never loaded anything), return at once so the spec acts under the load, and end leftovers before the health sample so they don't read as a degraded device.

## 5. Project integration

### 5.1 Layout

```
<project skill>/
  SKILL.md                     # accounts, device setup and quirks; takes a scope, delegates the run to soundcheck:run
  suite.yaml                   # with `specs: suite`
  _suite.md                    # optional: what every tester needs to know, whatever its spec
  hooks/                       # the project's hook scripts, each self-contained
  scripts/                     # what specs' `prepare` steps run (seeding, signing in)
  fixtures/                    # files testers can push onto a device
  suite/                       # only the specs
    <feature>/
      _feature.md              # shared context: how to get there, label hints, platform differences
      001-<name>.spec.md
```

Scaffolding sits beside `suite.yaml` (a suite with its specs in its own folder skips `hooks`, `scripts` and `fixtures` as features); the specs folder holds nothing but features, so it reads as the description of what's tested.

**`_suite.md`** (SA-1057, Aled 2026-11-25) holds the facts every tester needs whatever its spec, such as the test accounts' names. It goes into every brief as "About this app's suite", after the feature's `_feature.md`, and into the run's snapshot. It's optional. A tester reads only its brief, so anything a spec points at has to be in it: a Solo Scores spec pointed at "the second test account the regression skill names", which no tester can read, and lost an attempt.

### 5.2 `suite.yaml`

- `soundcheck: <version>`: the pin (section 8).
- `platforms`: a block per platform, named by the project (`ios`, `iphone`, `web`…; specs' `platforms:` use these names). **Each block is the whole map of how that platform runs** (SA-880..882, 0.3): nothing is shared from the top level or filled in by a placeholder, so two platforms repeat what they have in common, and what a platform runs is read from its own block. Hook scripts can still be one shared file; the config says which. Adding a platform is a new block; a new _kind_ of device (a headset) needs a driver in soundcheck first, then it's config too.
  - `driver`: required, `ios`, `android` or `chrome`: what soundcheck drives it with (section 4). Separate from the name, so two platforms can share a driver.
  - `device`: required, what the app runs on. For `ios`, a simulator's name (unique among the installed runtimes) or UDID; for `android`, an AVD name or adb serial; two platforms can't name the same one, and one that isn't running is booted headless (4.3; by AVD name only). Each device's reader has its own port, from the UDID on ios and the console port on android, so platforms on one driver run side by side (Aled, 2026-11-05: the `SOUNDCHECK_IOS_UDID` and `ANDROID_SERIAL` overrides are gone). For `chrome`, `desktop`, the only kind so far; each platform gets its own Chrome.
  - `app` (`ios`, `android`): the app ID the driver launches.
  - `chrome` only: `viewport`, required, the window's size (`1440x900`) at every reset unless a spec sets its own (5.4); `url`, where a launch opens; and optionally `chrome-profile`, a Chrome profile signed in to Google by hand with `soundcheck chrome-profile`: each run starts from a copy, since Google's sign-in refuses an automated browser and its session must already be there.
  - `hooks`: the commands in 5.3, all of them, for this platform.
  - `proxy`: optional, this platform's routes (below).
  - The platform block answers "how do you get the app or site running?". It has no home screen, seed or sign-in: how a spec is readied, signed in and opened is the spec's `prepare` (5.6), and what each screen looks like is in its prose.
- `specs`: the folder holding the feature folders (default: the suite folder itself).
- `reports`: where runs are written.
- `models`: `default`, the testers' model (`sonnet`), which a spec's `model` overrides, and `reviewer`, the reviewers' (`opus`; SA-1050, 3.3).
- `parallel`: false by default.
- `tickets`: how to link a ticket ID, for a project with a tracker; leave it out to keep findings in the report.
- `remote`: optional. `allow` lists the Google accounts that may open the page through `--remote` (3.1); `--remote` refuses to start a tunnel without it.
- Since 0.3 the 0.2 shape is refused (top-level `hooks`, `network`, `prepare`, `seeds`; a platform's `prepare`, `ready`, `account`, `app-id`, `base-url`, `profile`, `start` or `seed` hook; `{platform}` and `{account}`; a platform without `driver` or `device`; a spec's `seed` or `start`) by name, with a pointer to MIGRATIONS.md. There's no compatibility reading: Solo Scores moves in step.

A platform's `proxy` lists routes, each `{ name, listen, upstream }`: the app's test build reaches `listen`, and `upstream` really serves it. `upstream` is a port on this machine, or a remote service's URL (`https://api.revenuecat.com`, optionally with a port; `http://` too), so `offline` can take away a service the app would otherwise reach directly, such as a store SDK pointed at the proxy. The app still talks plain HTTP to `listen`; for a URL the proxy opens TLS itself, verifying the service's certificate against Mozilla's roots, and sets `Host` to the remote host on every request of a kept-alive connection. Drops, `offline` and faults behave the same for both kinds. A URL with a path, query or user, or any scheme but `http`/`https`, fails suite.yaml's parse, so lint reports it. Soundcheck knows ports and hosts only; which services exist and why is the project's business. `soundcheck proxy serve` runs the proxies (a run or `soundcheck drive` starts it, detached, when it isn't up, and it keeps running between runs so the test build always reaches its services; one started before the installed soundcheck was built is replaced, so it never lacks a command); `status` and `stop` manage it. Android forwards each route with `adb reverse` from its `device` port (default: `listen`) to `listen`; the iOS simulator and Chrome share the Mac's ports. Web has no network switch of its own: Chrome's DevTools network emulation, its fallback without routes, was dropped (2026-11-03) so every platform's network behaves alike, and lint asks for routes on each platform a spec using a network tool runs on. Each platform has its own proxy process (and command socket), so `offline`, `network-drop` and `fault` act on that platform alone (SA-779), and a route's `device` port lets every Android build keep the same ports while each platform's proxy listens on its own. Android's health puts back a forward that was dropped or aimed elsewhere (a build script once pointed them at the other platform's proxy). Listen ports are unique across platforms, and lint says which two collide. That has a cost for two platforms on the Mac's network (two `ios` platforms, or `ios` and `chrome`): they can't share a build whose ports are baked in, so each gets a build of its own pointed at its own ports, which the project's `install` hook makes.

### 5.3 Hooks

Hooks are shell commands, so a project writes them in anything. The contract is exit code 0 for ok, plus JSON on stdout where data comes back. The project resets data; the driver launches the app, because launching is generic.

| Hook                  | Called                                                                                                                                            | Returns                                                   |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| `guard`               | Run start, and before every reset                                                                                                                 | ok, or a refusal reason on stderr                         |
| `build-identity`      | Run start and after installs (gets the driver's app facts on stdin)                                                                               | `{ "commit", "fingerprint", "version" }` for its platform |
| `install`             | Run start, for a platform whose build can't be identified (every platform with `--install`); a coordinator's `install_build` with `install: true` | ok                                                        |
| `serve`               | Optional: run start and after every `install`; a process that runs until the server stops (a web build served at `url`)                           | ok once it serves                                         |
| `check {name} [args]` | When a tester calls `check-data`                                                                                                                  | JSON evidence (e.g. a database check)                     |
| `stack-up`            | Optional, with `stack-down`: run start, before the guard (3.11)                                                                                   | ok once the platform's blank backend answers              |
| `stack-down`          | When the run's server stops, or after one that died (3.11)                                                                                        | ok, also when there's nothing to remove                   |

Every hook is a platform's own (5.2) and runs for that platform alone: a guard once per platform at run start, `check` and `act` for a tester on that platform. The command names its platform, stack or account itself; the only placeholders left are the call's own arguments (a check's name and args). `guard`, `build-identity`, `install` and `check` are required; `serve` is optional on any platform, and `stack-up` and `stack-down` come as a pair. `install` makes the build current and is skipped when `build-identity` says it is; `serve` keeps what a platform needs running (on `chrome`, the site), so a build that's current still gets served.

Every hook, and every prepare step, gets `SOUNDCHECK_UNCOMMITTED=1` in a trial on uncommitted code (`run --uncommitted`, 3.12), and nothing extra otherwise.

Hooks are the platform's (how the app gets running, and the tester's data checks); readying a spec is its own `prepare` (5.6). Every spec starts from its own full `prepare`: no skipping and no snapshots. A spec never relies on state another spec left behind, so a rerun is independent and results can't depend on run order.

### 5.4 Spec format

```markdown
---
title: Draw a pen stroke, undo and redo it
platforms: [android, ios, chrome]
prepare: # optional: commands run after the relaunch, in order (5.6)
  - node scripts/seed.js viewer # prints {"values": {"SCORE": "…"}, "context": {...}}
  - node scripts/sign-in.js
  - ios: soundcheck drive ios open "myapp://viewer/$SCORE"
    android: soundcheck drive android open "myapp://viewer/$SCORE"
    chrome: soundcheck drive chrome open "/app/viewer/$SCORE"
viewport: 1440x1500 # optional, `chrome` only: this spec's window size instead of the platform's
model: sonnet # optional; ask for a stronger model for visual judgement
tools: [double-tap] # driver tools beyond the basics, if any
past-bugs: [SA-611]
proven-failing-on: []
---

## Goal

Draw a level stroke with the pen, undo it, redo it.

## Outcomes

- The stroke disappears on undo and returns in the same place on redo.
- Undo and Redo enable and disable to match.

## Probe around it

Undo straight after the first stroke; undo twice quickly.
```

- **Every spec is isolated:** a fresh relaunch, its own `prepare` (data, who is signed in, where it starts), and no reliance on another spec, so it can run alone, in any order, or again. Without `prepare` it starts on a fresh launch.
- **The path is the identity and the order** (`annotations/001-draw`). A renamed spec starts a fresh history.
- **Sections:** `## Goal` and `## Outcomes` (a `- ` list) are required; `## Probe around it` is optional, and so is `## Pinned`: exact steps, only where they guard a past bug or reach a control an agent can't discover.
- **Each outcome is judged on its own** (held, failed, unsure, couldn't check), with evidence; the spec's result follows from them (3.3).
- **A seen bug gets a regression spec:** more specific instructions, plus a probe around the old failure. Mechanics an agent can't do are driver tools the spec names; boundaries are data its `prepare` sets up.
- **The title is the user's goal.** No tap paths or tool commands.
- **Outcomes are what a user would notice.** Exact copy only for destructive or blocking messages, and no layout details a design tweak would break.
- **Platform differences go in `_feature.md` hints,** not separate specs. Where a spec's own wording differs (chrome ticks a box where the app organises first), a line starting with a tag, `[chrome]` or `- [android, ios]`, in any section, reaches only those platforms' testers; untagged lines reach every platform (Aled, 2026-11-02, SA-829: testers misread "(on web, …)" asides as applying to them). Each platform's outcomes are numbered on their own, which is safe because every result keeps the wording it judged. Lint refuses a tag naming a platform the spec doesn't list or naming all of them, and a platform left with no outcome.

### 5.5 Lint

`soundcheck lint <suite>` checks:

- frontmatter is valid;
- IDs are unique;
- platforms are the suite's (with the nearest name when one isn't), in `platforms:`, line tags and `prepare` maps;
- a `prepare` map names every platform the spec lists (`true` for nothing on one), a step's script path exists, and a `soundcheck drive <platform>` in a map entry names that entry's platform;
- the tools exist in the driver;
- titles follow the rules;
- every spec has a Goal and Outcomes.

### 5.6 Prepare (SA-881, SA-882, Aled 2026-11-05)

A spec's `prepare` is everything scripted that has to happen before it runs; anything after that is the tester's, in the spec's prose. Two levels, kept apart: the platform block answers "how do you get the app or site running?" (5.2, the same for every spec), and `prepare` answers "how do I ready this spec?".

- **A step is a command:** a script, a bash line, anything runnable from the suite folder. A plain string runs on every platform the spec lists; a map gives one per platform and names every one of them, with `true` for a platform where the step does nothing.
- **The abstraction is the script, not the spec.** Every step a spec takes is readable in it. A pattern that repeats becomes a script; soundcheck has no aliases, recipes, defaults, seeds, sessions or start links. Seeding, signing in and where to start are the project's, in its scripts, or not at all.
- **The harness runs the steps.** At every reset: `guard`, a fresh relaunch, then each step in order. Not after the last: the tester starts where `prepare` left the app. A step that needs another relaunch (after `clear`) runs it itself. A step exiting non-zero or running past `--prepare-timeout` (a `run` flag, default 60 s) is a reset error (3.2). soundcheck doesn't care what a step does or who wrote it.
- **Each step's environment:** `SOUNDCHECK_PLATFORM`, `SOUNDCHECK_DRIVER`, `SOUNDCHECK_DEVICE`, `SOUNDCHECK_BIN` (this soundcheck's executable, which every hook gets too, so a script never drives with another version from the PATH), the running server's address (so `soundcheck drive` acts on the run's device, not a second one), `SOUNDCHECK_UNCOMMITTED=1` in a trial on uncommitted code (3.12), and every value an earlier step printed.
- **Values are environment variables.** A step may print `{ "values": {...}, "context": {...} }`: each value becomes a variable for the steps after it (names must be valid variable names, `COLLECTION`; a bad one fails the reset), filled by the shell, so a step runs the same pasted into a terminal; `context` goes into the tester's prompt as compact JSON. The journal records commands as written, so a value, a token included, never reaches a report.

**soundcheck is the compatibility layer.** Steps call `soundcheck drive <platform> <tool> …`, the same commands testers and people use, always in that long form (a step may `tap` if it must). A tool is defined by its effect; soundcheck owns the mechanism on each driver, and each tool lists the drivers that implement it:

| Tool                                | Effect                                                 | `ios`                                                    | `android`                 | `chrome`                                                |
| ----------------------------------- | ------------------------------------------------------ | -------------------------------------------------------- | ------------------------- | ------------------------------------------------------- |
| `open <link>`                       | the app or site shows the link                         | `simctl openurl`                                         | `am start -d`             | navigate; a `/path` is on the platform's `url`          |
| `open --relaunch <link>`            | the app starts from the link                           | terminate, `simctl openurl`                              | force-stop, `am start -d` | navigate (a page load starts afresh)                    |
| `relaunch`                          | a fresh start                                          | terminate, launch                                        | force-stop, launch        | the platform's `url` loaded again                       |
| `clear-data`                        | the app's data is gone; relaunch after it              | empty its data container, reset the simulator's keychain | `pm clear`                | clear cookies and the site's storage                    |
| `cookies set name=value [--path p]` | the browser holds the cookie                           | no                                                       | no                        | `Network.setCookies` on the site's url                  |
| `storage set key=value`             | the site's origin holds the key, read at its next load | no                                                       | no                        | `localStorage` on the open page, which must be the site |

A tool on a driver without it fails with why ("cookies needs a browser; ios runs on the ios driver"), so a script on the wrong branch fails its reset rather than doing nothing. A link the app must not miss, such as a sign-in link, goes with `--relaunch`: `relaunch` returns once the app shows a screen, which on an app with a splash is before it listens for links, and React Native drops a link that arrives then; an app always reads the link it launched from (Aled, 2026-11-05). Inside a run a step gets `SOUNDCHECK_SERVER`, and `drive` sends the action to that server (`POST /drive`), which acts on the device the run holds; without it, `drive` connects to the device itself. `clear-data` on ios leaves the keychain empty for every app on that simulator, the system's own included, so it signs the simulator out of its Apple ID: a suite with Sign in with Apple signs out through the app instead (Solo opens a sign-out link). It is quick because nothing is reinstalled (Aled, 2026-11-05; `clear`, the focused field's tool, keeps its name). A new driver (Firefox) brings its own implementation behind the same commands. soundcheck makes the mechanism the same, not the link: `myapp://viewer/x` against `/app/viewer/x` is the app's routing, so the spec maps it per platform, or a project script does.

`create-test` runs it after every edit, and `run` refuses an invalid suite.

## 6. Plugin

The soundcheck repo ships as a Claude Code plugin:

- **The `soundcheck` binary,** built on install.
- **MCP config** for the local server, which the coordinator's session uses.
- **One hook, `SessionStart`,** which tells a new session about a run that's up (3.2). The hooks that made a coordinator dispatch, kept it from stopping and counted testers' tokens went with SA-1049.
- **No agent types** (SA-1049, Aled 2026-11-25). `soundcheck-tester`, `soundcheck-tester-mechanics` and `soundcheck-reviewer` are defined in the server, which launches them itself with only their own tools (3.2, 3.3): a tester can't read app source, run shell or edit files, and a reviewer can read the project but change nothing. The plugin's `agents/` folder went, and a test keeps it gone.
- **Skills:**
  - **`setup`:** interviews the person, then scaffolds `suite.yaml`, hook stubs and a draft project skill. On a suite pinned to an older version, it migrates the suite and shows the diff for review.
  - **`run`:** the generic coordinator procedure: start the server, wait on `soundcheck attention`, deal with what it prints, close, triage, export. A project skill passes the scope it was given (platforms, specs or features) with a line on what the run is testing, for the reviewers, and delegates to it; choosing the scope belongs to whatever calls it, such as a release process.
  - **`create-test`:** add or change specs. Search for duplicates first, turn a found bug into a regression spec, add to the project's prepare scripts when needed, and finish with lint.
  - **`drive`:** use a device by hand outside a run (look at a screen, reproduce a bug, check a change, set up a screenshot) through `soundcheck drive`. It adds nothing `drive` can't already do: it's there so a session asked to look at the app finds the commands without loading a regression skill and treating a look as a test run (Aled, 2026-10-23).

## 7. Verdict rules

- **Any open FAIL blocks the release,** whichever spec it's on. There are no special gate tests.
- **A BLOCKED** goes through review and triage like a FAIL. One blocked by a harness gap, not the app, goes in the run's notes, and its spec counts as not run until a rerun passes.
- **Verdict:**
  - **Failing:** any open failure. (Not "Blocked", which a row means when the environment or harness stopped its test.)
  - **Not ready:** an open (untriaged) problem, specs not run, or results still under review.
  - **Ready:** otherwise.
- **BLOCKED means the environment or harness stopped the test, never the app** (Aled, 2026-10-21). It isn't a result about the app: the row shows purple with one line saying why, counts as not tested until a rerun passes, and keeps the verdict at Not ready. Reset failures, stuck devices, missing labels and tool gaps are all BLOCKED. If the app stopped the test, it's a FAIL.
- **Problems are app bugs and findings only.** Harness gaps and device glitches go in the run's notes.
- **Triage outcomes** (3.3):
  - **Dismissed:** not a bug, or not reproduced. A problem that only passed on a rerun is Dismissed, never Fixed.
  - **Fixed:** a fix landed. Needs a ticket when the suite names a tracker.
  - **Deferred:** accepted for this release. Needs a ticket when the suite names a tracker.
- **Failure or finding, never a severity** (Aled, 2026-10-21). A **failure** blocks the release until it's triaged: every upheld FAIL, including a test the app stopped. A **finding** doesn't block but still needs a decision: side finds, "not reproduced" ones, UX or accessibility observations. "Not exactly the test case, but something to think about." The kind follows from where the problem came from, so no reviewer grades it, and a confirmed FAIL can't be labelled anything milder.
- **Duplicates fold into the original** (`duplicateOf`).

## 8. Versioning

- The suite pins a version in `suite.yaml`. The server refuses a suite pinned to an incompatible version, and `setup` offers the migration. The pin is matched on the minor version: 0.4 refuses a suite pinned to `"0.3"`, and lint says to run the setup skill, which follows the plugin's MIGRATIONS.md. For 0.4 the suite's shape is unchanged and only the pin moves; what changes is around the suite (3.2, 3.3).
- The plugin, binary and skills share one version, so a skill and the server never drift apart.
- A soundcheck upgrade never lands mid-release.

## 9. Build order

Built against Solo Scores, which proves the concept; there's no separate demo app. The harness's own tests are unit tests against a fake driver, plus recorded device trees for the parsers and parity checks.

1. **Server core (device-free):**
   - Cargo workspace;
   - spec loader, `suite.yaml` schema, lint;
   - journal and row states with their rules;
   - verdict logic;
   - unit tests against a fake driver.
2. **Suite migration:** convert Solo Scores' guides into specs with `create-test` and lint, applying its cleanup backlog in the same pass.
3. **MCP and live page:** the HTTP server, testers' and coordinator's tools, the event stream, the live page. The device tools call Solo Scores' existing `ui.mjs` underneath, so a full run works end to end.
4. **Rust drivers:** Android and iOS behind the interface, with embedded readers, the element model, parity tests, `check`, `batch` and the mechanic tools. They replace `ui.mjs` behind the same MCP tools.
5. **Report port and export.**
6. **Web driver** with its parity test. Web is also the natural first target for CI.
7. **First real run** when ready. It's Solo Scores' next focus.
8. **Later:** parallel platforms (done, SA-779), headless dispatch (done 2026-11-25, SA-1049 and SA-1050: the server launches headless Claude Code processes itself, rather than going through the Agent SDK), phone notifications off the event stream, a second app.

## 10. Open questions

- **Licence:** MIT (decided 2026-10-21, `LICENSE`); the iOS reader follows AXe's MIT code.
- **Port:** 7357 by default. The plugin's MCP server is `soundcheck mcp`, a stdio bridge that lists the tools from the start and forwards each call to the run serving on the port, so a session opened before `soundcheck run` needs no reconnect (decided 2026-10-21, after the first run).
- **One server holds the port** (SA-697, Aled 2026-10-25). A finished run's server stays up, so its page and triage keep working, until a new run needs the port. A new run asks first, before any hook: a finished run with no tool call for 5 minutes, or a `soundcheck serve` reports server, steps down, and its report stays under `/runs`. An unfinished run, or a finished one used in the last 5 minutes (triage may be under way), keeps the port, and the new run refuses with its folder and how to resume or stop it. Before this, a second run found the port taken only after its builds.
- **The tester's silence timeout** before a running spec is treated as stopped.
- **Building while a device runs** (open, SA-1055): building Android with the emulator up overloaded the Mac in run 2d469187 (load about 60), and the emulator restarted mid-install. Not built.
- **A commit in the app's repository mid-run** (open, SA-1056) halts dispatch, since the `build-identity` hook compares the installed build with the working tree. One idea: a worktree pinned to the run's commit. Not built.
- **Web start hook** (answered 2026-11-03, SA-840): it serves a production build that the `install` hook made, and the build identity reads that install's record, as on the phones.
- **Android overlay gap** (answered 2026-10-21): neither timing nor the long-lived connection. The controls are drawn outside their parent's bounds, so Android reports them invisible with an empty frame to uiautomator as well; an app fix (4.2).
- **The parity screen set** (answered 2026-10-21, 4.3): reached by hand with `drive`, since how to reach screens is the app's knowledge; a project could script it from its specs later.
